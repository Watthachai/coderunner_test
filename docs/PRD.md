# PRD — ExpenseFlow

## 1. ภาพรวม
ExpenseFlow คือระบบบันทึกเคลมค่าใช้จ่ายและเงินทดรองจ่าย (Expense Claim & Cash Advance Management) ที่ออกแบบมาสำหรับ Digitalvalue (องค์กรที่ปรึกษาขนาด 10 คน) เพื่อเปลี่ยนผ่านจากระบบเอกสารกระดาษ/แชทไลน์ ไปสู่ระบบดิจิทัลที่สามารถควบคุมงบประมาณ เงินทดรองจ่ายค้างเคลียร์ และวิเคราะห์ค่าใช้จ่ายได้แบบ Real-time (อ้างอิง: docs/BRD.md) โดยเน้นความง่ายในการใช้งานบน Mobile สำหรับพนักงาน และ Desktop สำหรับฝ่ายบัญชีและผู้บริหาร

## 2. หน้าจอทั้งหมด
| # | หน้าจอ | ทำหน้าที่ | ส่วนประกอบหลัก |
|---|---|---|---|
| P-01 | **Dashboard (Desktop/Mobile)** | แสดงภาพรวมการเงินและ KPI สำหรับผู้บริหารและบัญชี | - การ์ดยอดรวมสะสม (Total Expense, Active Advance)<br>- กราฟวงกลม (Pie Chart) แยกตามแผนกและหมวดหมู่<br>- ตาราง Aging Report: รายชื่อพนักงานที่ถือเงินทดรองจ่ายค้างเคลียร์นานที่สุด (> 15 วัน) |
| P-02 | **My Requests (Mobile-First)** | หน้าจอสำหรับพนักงานดูสถานะและสร้างคำขอใหม่ | - รายการเอกสาร ADV และ EXP ของตนเอง พร้อมสถานะ<br>- ปุ่ม "ขอเงินทดรองจ่าย (ADV)" และ "เบิกค่าใช้จ่าย (EXP)"<br>- ฟังก์ชันสลับบทบาท (Role Switcher) ด้านบนสุดสำหรับ Demo |
| P-03 | **Request Form & OCR (Mobile-First)** | ฟอร์มสร้างเอกสารและระบบสแกนใบเสร็จ | - ช่องอัปโหลดรูปใบเสร็จ + ปุ่ม "สแกนด้วย OCR"<br>- ฟอร์มกรอกข้อมูล (วันที่, ยอดเงิน, ร้านค้า, หมวดหมู่, แผนก)<br>- ส่วนอ้างอิงใบ ADV (กรณีต้องการเคลียร์เงินทดรองจ่าย) |
| P-04 | **Approvals (Desktop/Mobile)** | หน้าจอสำหรับหัวหน้าแผนกและบัญชีเพื่ออนุมัติ | - รายการเอกสารที่รออนุมัติ (Pending Approval)<br>- หน้าจอแสดงรายละเอียดเอกสาร + รูปใบเสร็จ<br>- ปุ่ม "อนุมัติ (Approve)" และ "ปฏิเสธ (Reject)" พร้อมช่องกรอกเหตุผล |
| P-05 | **Finance Settlement (Desktop)** | หน้าจอสำหรับฝ่ายบัญชีจัดการจ่ายเงินและส่งออกข้อมูล | - รายการเอกสารที่ผ่านการอนุมัติแล้ว (Approved)<br>- ปุ่ม "บันทึกการจ่ายเงิน (Mark as Paid)" สำหรับ ADV และ EXP<br>- ปุ่ม "ยืนยันรับเงินคืน (Confirm Refund)" สำหรับ ADV ที่เคลียร์ยอดไม่หมด<br>- ตัวกรองช่วงเวลา + ปุ่ม "Export CSV" |

## 3. User Stories
| รหัส | ในฐานะ… ฉันต้องการ… เพื่อ… | เกณฑ์การยอมรับ (Given/When/Then) |
|---|---|---|
| **US-01** | **พนักงาน**<br>ต้องการอัปโหลดรูปใบเสร็จและให้ OCR ดึงข้อมูลอัตโนมัติ | **Given:** พนักงานอยู่ที่หน้าจอสร้างใบเบิกค่าใช้จ่าย (EXP)<br>**When:** พนักงานอัปโหลดรูปใบเสร็จและกด "สแกนด้วย OCR"<br>**Then:** ระบบต้องดึงข้อมูล วันที่, ยอดเงินรวม, และชื่อร้านค้า มากรอกในฟอร์มโดยอัตโนมัติ และอนุญาตให้พนักงานแก้ไขข้อมูลในฟอร์มได้หาก OCR อ่านผิดพลาด |
| **US-02** | **พนักงาน**<br>ต้องการเคลียร์เงินทดรองจ่าย (ADV) ด้วยใบเบิกค่าใช้จ่าย (EXP) | **Given:** พนักงานมีใบ ADV สถานะ "Paid" ยอดเงิน 5,000 บาท<br>**When:** พนักงานสร้างใบ EXP โดยเลือกอ้างอิงใบ ADV ดังกล่าว<br>**Then (กรณีใช้ไม่หมด):** หากกรอกยอดใช้จริง 4,500 บาท ระบบต้องยอมรับ และคำนวณเงินทอน 500 บาทให้อัตโนมัติ<br>**Then (กรณีใช้เกิน):** หากกรอกยอดใช้จริง 5,500 บาท ระบบต้องแสดงข้อความเตือน "ห้ามเบิกเกินยอดเงินทดรองจ่าย" และไม่อนุญาตให้บันทึก (พนักงานต้องเคลมเท่ากับ 5,000 บาท และไปสร้างใบ EXP ปกติแยกอีกใบเพื่อเบิก 500 บาทที่เหลือ) |
| **US-03** | **ฝ่ายบัญชี**<br>ต้องการเคลียร์สถานะใบขอเงินทดรองจ่ายที่ใช้เงินไม่หมด | **Given:** ใบ ADV ยอด 5,000 บาท ถูกเคลียร์ด้วยใบ EXP ยอด 4,500 บาท (สถานะ ADV เป็น "Pending Refund" ยอดค้าง 500 บาท)<br>**When:** ฝ่ายบัญชีได้รับเงินสด/เงินโอนคืนจากพนักงานนอกระบบ และกดปุ่ม "Confirm Refund" บนระบบ<br>**Then:** สถานะของใบ ADV นั้นต้องเปลี่ยนเป็น "Settled" (เคลียร์แล้ว) และยอดเงินทดรองจ่ายค้างเคลียร์บน Dashboard ต้องลดลง 5,000 บาททันที |
| **US-04** | **ผู้อนุมัติ (หัวหน้า/บัญชี)**<br>ต้องการปฏิเสธคำขอที่ไม่ถูกต้อง | **Given:** ผู้อนุมัติเปิดดูคำขอที่สถานะ "Pending Approval"<br>**When:** ผู้อนุมัติกดปุ่ม "Reject" โดยไม่กรอก "เหตุผลการปฏิเสธ"<br>**Then:** ระบบต้องแสดงข้อความเตือนและไม่อนุญาตให้ส่งคำขอ<br>**When:** ผู้อนุมัติกรอกเหตุผลและกดยืนยัน Reject<br>**Then:** เอกสารเปลี่ยนสถานะเป็น "Rejected" และส่งกลับไปให้พนักงานแก้ไขได้ |

## 4. ข้อมูลและฟิลด์
### 4.1 ข้อมูลผู้ใช้งาน (User Master Data)
* `user_id` (String, บังคับ): รหัสพนักงาน เช่น `EMP001`
* `full_name` (String, บังคับ): ชื่อ-นามสกุล
* `email` (String, บังคับ)
* `department` (Enum, บังคับ): `Management`, `Consulting`, `Delivery`
* `role` (Enum, บังคับ): `Employee`, `Approver`, `Finance`

### 4.2 ใบขอเงินทดรองจ่าย (Cash Advance Document - ADV)
* `document_no` (String, บังคับ): Format `ADV-2026-XXXXX` (รันอัตโนมัติ)
* `request_date` (Date, บังคับ): วันที่สร้างคำขอ
* `requester_id` (String, บังคับ): อ้างอิง `user_id`
* `amount` (Decimal, บังคับ): ยอดเงินที่ขอ (THB เท่านั้น, > 0)
* `purpose` (String, บังคับ): วัตถุประสงค์การขอเงิน
* `status` (Enum, บังคับ): `Draft` -> `Pending Approval` -> `Approved` -> `Paid` -> `Pending Refund` (กรณีใช้ไม่หมดและรอเงินทอน) -> `Settled` (เคลียร์ครบแล้ว) / `Rejected`
* `reject_reason` (String, เลือกกรอกได้): บังคับกรอกหากสถานะเป็น `Rejected`

### 4.3 ใบเบิกค่าใช้จ่าย (Expense Claim Document - EXP)
* `document_no` (String, บังคับ): Format `EXP-2026-XXXXX` (รันอัตโนมัติ)
* `advance_ref` (String, เลือกกรอกได้): อ้างอิง `document_no` ของ ADV (ถ้ามี)
* `receipt_date` (Date, บังคับ): วันที่ตามใบเสร็จ
* `amount` (Decimal, บังคับ): ยอดเงินรวม (THB เท่านั้น, > 0)
* `category` (Enum, บังคับ): `Travel` (ค่าเดินทาง), `Entertainment` (ค่ารับรอง), `Office Supplies` (ค่าอุปกรณ์), `SaaS/Software` (ค่าซอฟต์แวร์), `Others` (อื่นๆ)
* `department` (Enum, บังคับ): `Management`, `Consulting`, `Delivery` (สืบทอดจากแผนกของผู้ขอโดยอัตโนมัติ แต่แก้ไขได้)
* `supplier_name` (String, บังคับ): ชื่อร้านค้าที่ออกใบเสร็จ
* `payment_method` (Enum, บังคับ): `Cash`, `Transfer`, `Credit Card`
* `receipt_image_url` (String, บังคับ): URL รูปภาพใบเสร็จที่อัปโหลด
* `description` (String, เลือกกรอกได้): รายละเอียดเพิ่มเติม
* `status` (Enum, บังคับ): `Draft` -> `Pending Approval` -> `Approved` -> `Paid` / `Rejected`

## 5. Design Spec
* **Theme & Colors:**
  - สีหลัก (Primary): Indigo Blue (`#4F46E5`) สำหรับปุ่มหลัก, Header, และจุดเน้นย้ำ
  - สีพื้นหลัง (Background): เทาอ่อน (`#F9FAFB`) และสีขาว (`#FFFFFF`) สำหรับ Card
  - สีสถานะ (Status Colors):
    - `Draft` / `Pending Refund`: สีส้ม/เหลือง (`#F59E0B`)
    - `Pending Approval`: สีน้ำเงินคราม (`#3B82F6`)
    - `Approved` / `Paid` / `Settled`: สีเขียว (`#10B981`)
    - `Rejected`: สีแดง (`#EF4444`)
* **Typography:** ใช้ฟอนต์ Sans-serif (เช่น Prompt หรือ Sarabun) เพื่อให้อ่านง่ายและดูทันสมัยสไตล์สตาร์ทอัพ
* **Layout:** Responsive Design โดยหน้าจอสร้างเอกสาร (My Requests/Form) ต้องรองรับการทำงานบน Mobile 100% (ปุ่มกดใหญ่ ถ่ายรูปง่าย) ส่วนหน้าจอ Dashboard และ Finance Settlement ให้เน้นการแสดงผลบน Desktop เป็นหลัก

## 6. Non-functional Requirements
* **Performance:** หน้าจอ Dashboard ต้องโหลดและคำนวณยอด Real-time เสร็จสิ้นภายใน 1.5 วินาที
* **Data Validation:**
  - ป้องกันการแนบรูปใบเสร็จซ้ำ (Duplicate Detection): หากมีการสร้าง EXP ใหม่ที่มี ยอดเงิน + วันที่ใบเสร็จ + ชื่อร้านค้า ตรงกับเอกสารเดิมในระบบ ให้แสดงคำเตือน (Warning) ให้พนักงานตรวจสอบก่อนยืนยัน
  - บังคับให้พนักงานต้องตรวจสอบและกดยืนยันข้อมูลที่ได้จาก OCR เสมอเพื่อป้องกันความผิดพลาดจาก AI
* **Security & Roles:** ระบบต้องมีการจำกัดสิทธิ์ (Role-based Access Control) อย่างเข้มงวด:
  - พนักงานเห็นเฉพาะเอกสารของตนเอง
  - หัวหน้าแผนกเห็นเอกสารของพนักงานทุกคนในแผนกตนเองเพื่อกดอนุมัติ
  - ฝ่ายบัญชีเห็นเอกสารทั้งหมดในระบบ และเป็นคนเดียวที่มีสิทธิ์กด "Paid", "Confirm Refund" และ "Export CSV"

## 7. ขอบเขตของ demo (Out of Scope)
* **ไม่มีระบบสแกน Line Items:** OCR จะดึงเฉพาะข้อมูล 3 ฟิลด์หลัก (วันที่, ยอดรวม, ร้านค้า) เท่านั้น ไม่มีการแยกรายการสินค้าในใบเสร็จ
* **ไม่มี Real-time ERP API:** การเชื่อมต่อกับระบบบัญชีภายนอกจะทำผ่านการดาวน์โหลดไฟล์ Standard CSV เท่านั้น (ประกอบด้วยฟิลด์: วันที่, เลขที่เอกสาร, แผนก, หมวดหมู่, ยอดเงิน, ร้านค้า, วิธีการจ่าย, คำอธิบาย)
* **ไม่มีระบบโอนเงินจริง (No Bank Gateway):** การจ่ายเงินพนักงานและการรับเงินทอนคืนจะทำนอกระบบทั้งหมด ระบบนี้ใช้เพื่อบันทึกสถานะทางบัญชี (Mark as Paid / Confirm Refund) เท่านั้น
